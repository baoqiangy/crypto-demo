CCM — Counter with CBC-MAC

How AES-CTR and CBC-MAC work together to protect confidentiality, integrity, and authenticity

CCM is an authenticated encryption with associated data (AEAD) mode. It combines Counter (CTR) mode, which encrypts the plaintext, with CBC-MAC, which authenticates the plaintext and optional associated data. CCM is standardized in NIST SP 800-38C.

ConfidentialityCTR mode hides the plaintext.
IntegrityAuthentication detects modifications.
AuthenticityA valid tag proves knowledge of the secret key.

1. Inputs and outputs

SymbolMeaning
KShared AES key (128, 192, or 256 bits)
NUnique nonce (7–13 bytes for CCM)
PPlaintext to encrypt and authenticate
AAssociated data: authenticated but not encrypted (e.g., packet header)
tAuthentication tag length: 4, 6, 8, 10, 12, 14, or 16 bytes
C, UEncrypted plaintext and transmitted authentication tag
(K, N, P, A) → CCM encryption → (C, U)

The receiver uses K, N, A, C, and U to check integrity and recover P only if authentication succeeds.

2. Two operations inside CCM

CCM is an authenticate-then-encrypt construction: CBC-MAC computes a tag; CTR encrypts the plaintext and masks the tag.

3. Step 1 — Compute the CBC-MAC

CCM creates a precisely formatted series of 128-bit blocks, starting with a control block B₀ that includes flags, the nonce, and plaintext length. Encoded associated data (if present) follows, then the plaintext. The formatting encodes lengths and parameters to avoid the variable-length attacks that affect naive CBC-MAC.

B₀ = Flags || N || encodeq(len(P))
X₀ = 0¹²⁸
Xᵢ = AESK(Xᵢ₋₁ ⊕ Bᵢ₋₁), for i = 1,…,r+1
T = MSB8t(Xr+1)

Here q = 15 − len(N) bytes are used to represent the plaintext length, and MSB selects the first t bytes. The formatted blocks are B₀ … Bᵣ.

4. Step 2 — Encrypt with CTR mode

CCM constructs counter blocks A₀, A₁, A₂, … using the same nonce and separate counter values. AES encryption of these blocks creates a keystream:

Sᵢ = AESK(Aᵢ)
Cᵢ = Pᵢ ⊕ Sᵢ, for i ≥ 1
U = T ⊕ MSB8t(S₀)

Important: Counter block A₀ is reserved for masking the MAC tag; payload encryption starts with A₁. For a short final plaintext block, only the needed keystream bytes are used.

5. Worked example — How the operations fit together

Suppose a device sends a secure control command:

Key (K):        128-bit shared AES key
Nonce (N):      11-byte unique value
Associated data: Device ID = 42
Plaintext (P):  "OPEN"
Tag length:     8 bytes (64 bits)
  1. Set q = 15 − 11 = 4; encode the 4-byte plaintext length in B₀.
  2. Run CBC-MAC over the CCM-formatted control block, associated data, and plaintext to obtain the internal tag T.
  3. Generate S₁ = AESK(A₁); XOR its first four bytes with OPEN to create four bytes of ciphertext C.
  4. Compute S₀ = AESK(A₀) and mask the 8-byte MAC: U = T XOR first_8_bytes(S₀).
  5. Transmit the nonce, ciphertext, and masked tag; provide associated data to the receiver unchanged.
Teaching note: This example illustrates the operations without inventing AES outputs. Actual ciphertext and tag bytes depend on the chosen key and nonce.

6. Receiver verification

  1. Use the nonce and key to regenerate CTR keystream blocks.
  2. Decrypt the ciphertext to recover a candidate plaintext.
  3. Recompute CBC-MAC using the candidate plaintext, nonce, and associated data.
  4. Recompute the expected transmitted tag and compare it securely.
  5. Release plaintext only if the tag verifies. Otherwise reject the entire message.
Security rule: Do not act on unauthenticated plaintext. Implementations must withhold it until tag verification succeeds; a failed check must not leak partially decrypted data.

7. Why the nonce matters

The nonce is not a secret, and it need not be random, but it must be unique for each encryption with a given key. Reusing a nonce repeats CTR keystream bytes, allowing an attacker to learn the XOR of two plaintexts, and undermines CCM's security guarantees.

C₁ = P₁ ⊕ S,   C₂ = P₂ ⊕ S
Therefore: C₁ ⊕ C₂ = P₁ ⊕ P₂

Unique nonces are mandatory even if the messages differ. A nonce alone does not prevent replay: a receiver also needs replay-detection state, such as tracked sequence numbers.

8. Associated authenticated data (AAD)

AAD is protected against unauthorized modification but remains visible. Examples include packet headers, device identifiers, routing metadata, or protocol fields that must be authenticated without being encrypted.

DataEncrypted?Authenticated?
Plaintext payloadYesYes
Associated data (AAD)NoYes
NonceNoBound into CCM authentication and counter formatting

10. Python example (AES-CCM)

The following example uses a tested library implementation rather than implementing CCM's block formatting manually.

from cryptography.hazmat.primitives.ciphers.aead import AESCCM
import os

key = AESCCM.generate_key(bit_length=128)
aesccm = AESCCM(key, tag_length=8)
nonce = os.urandom(11)  # Must never repeat with this key
plaintext = b"OPEN"
aad = b"Device ID = 42"

# ciphertext includes the authentication tag at the end
encrypted = aesccm.encrypt(nonce, plaintext, aad)
print("Ciphertext + tag:", encrypted.hex())

# Raises InvalidTag if ciphertext, AAD, key or nonce is wrong
recovered = aesccm.decrypt(nonce, encrypted, aad)
print("Recovered:", recovered.decode())

Install the library with pip install cryptography. This example randomly generates a nonce for a single operation; real applications must enforce nonce uniqueness across all encryptions under the same key, including across process restarts.

11. Security considerations

  • Never reuse a nonce with the same key. Use a robust nonce-management scheme.
  • Choose sufficient tag length. Short tags allow higher forgery probability; the acceptable length depends on protocol limits and threat model.
  • Authenticate associated data exactly. Sender and receiver must use identical AAD bytes.
  • Reject failed authentication. Never process plaintext before verification.
  • Prevent replay at the protocol level. AEAD authentication does not imply freshness.
  • Use standard cryptographic libraries. Do not invent your own CCM formatting or encryption construction.
