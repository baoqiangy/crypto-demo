Cryptographic hash functions

Sponge Construction

How SHA-3 absorbs messages into a large internal state and squeezes out a hash digest.

1. The basic idea

A cryptographic sponge construction builds a hash function from a fixed-width permutation. Unlike a traditional Merkle–Damgård hash, which repeatedly applies a compression function to chaining values and message blocks, a sponge maintains a larger internal state, feeds input into part of it, and later extracts output from part of it.

The two main phases are absorbing (taking in the message) and squeezing (producing the hash). A sponge can produce a fixed-length digest, as SHA3-256 does, or a variable-length output, as SHAKE does.

Each padded message block is XORed into the rate portion. A permutation mixes the entire state. Squeezing reads rate bits and permutes again if more output is needed.

2. Rate, capacity, and state width

The internal state has a fixed width b bits, divided conceptually into a rate part (r bits) and a capacity part (c bits).

b = r + c

Rate determines how many message bits are absorbed per block and how many output bits are available between permutations. A higher rate generally increases throughput. Capacity contributes to the security margin and limits generic attacks. The capacity bits are not directly XORed with input blocks or returned as output, although the permutation mixes both portions.

Important: SHA3-256 has a 256-bit digest and a 512-bit capacity. These values describe different properties. A 256-bit hash has a generic collision-security ceiling of approximately 128 bits, while its generic preimage resistance is approximately 256 bits.

3. Absorbing the message

  1. Initialize the state: all b bits begin at zero.
  2. Pad the message: make its bit length a multiple of the rate r; domain-separation bits distinguish SHA-3 from related Keccak-based functions.
  3. Split the padded input into r-bit blocks P₀, P₁, …
  4. XOR each block into the first r bits of the current state.
  5. Apply the full-state permutation f after each absorbed block, including the last one.
S₀ = 0ᵇ
Sᵢ₊₁ = f(Sᵢ ⊕ (Pᵢ ∥ 0ᶜ))

The notation ∥ means concatenation, and ⊕ means bitwise XOR. Even though the block enters through the rate portion, the permutation mixes information throughout all b state bits.

Padding and domain separation

Keccak sponges use a multi-rate padding rule often written pad10*1: append a 1, then zero or more 0 bits, then a final 1 to fill a whole number of rate-sized blocks. Standardized SHA-3 also applies domain-separation suffix bits before the multi-rate padding. In common byte-oriented implementations, the combined initial suffix byte for SHA3 functions is 0x06; for SHAKE functions it is 0x1F. The last byte of the padded block has its high bit set (XOR with 0x80).

Do not confuse SHA3-256 with Keccak-256. Both use the same underlying Keccak permutation and rate/capacity parameters, but their padding/domain separation differs, so the hashes of the same message differ.

4. The Keccak-f[1600] permutation

SHA-3 uses Keccak-f[1600], a permutation over a 1600-bit state. The state is viewed as a 5 × 5 array of lanes, each lane 64 bits wide: 25 × 64 = 1600.

A[x,y] identifies a 64-bit lane. Each of the 24 rounds transforms all 25 lanes.

Each Keccak-f[1600] permutation consists of 24 rounds. Every round applies five transformations in this order:

StepPurposeConcept
θ (theta)Mix columnsEach lane depends on parities of nearby columns.
ρ (rho)Rotate bitsRotate each lane by its designated offset.
π (pi)Reposition lanesMove lanes to new locations in the 5×5 state.
χ (chi)Add nonlinearityApply a nonlinear Boolean relation among lanes of a row.
ι (iota)Break symmetryXOR a round-dependent constant into A[0,0].
θ → ρ → π → χ → ι   (repeat for 24 rounds)

The permutation is not a compression function. It maps a 1600-bit state to another 1600-bit state; input and output widths are equal.

5. Squeezing the output

After the last padded message block has been absorbed and permuted, output is taken from the first r bits of the current state. If more bits are required, apply the permutation again and take another r-bit segment. Repeat until enough bits have been produced, then truncate the output to the desired length.

Z = truncateₗ(rate(S) ∥ rate(f(S)) ∥ rate(f²(S)) ∥ …)

For SHA3-256, the output is only 256 bits while the rate is 1088 bits, so all 256 output bits come from the first squeezing segment; no additional squeeze permutation is required. SHAKE, by contrast, can continue producing output for as long as needed.

6. Worked example: SHA3-256("abc")

ASCII abc corresponds to three bytes:

61 62 63 (hex) = 24 bits
  1. Initialize a 1600-bit zero state.
  2. Append the SHA3-256 suffix/padding. For this short message, the 136-byte (1088-bit) padded block starts with 61 62 63 06, contains zeros, and has 80 as its final byte.
  3. XOR the padded block into the first 1088 state bits.
  4. Apply the 24-round Keccak-f[1600] permutation.
  5. Read the first 256 output bits, using Keccak's byte/lane ordering.

The standardized result is:

SHA3-256("abc") =
3a985da74fe225b2045c172d6bd390bd
855f086e3e9d525b46bfe24511431532

Even though the message contains only 24 bits, the algorithm returns a 256-bit (64-hex-character) digest. That does not mean hashing created 256 bits of uncertainty in the original message.

7. Security and design tradeoffs

Benefits

The sponge construction naturally supports variable-length output and domain-separated functions. Because it uses a full-state permutation instead of exposing a final chaining state as a digest, classic Merkle–Damgård length-extension reasoning does not transfer directly.

Constraints

Security depends on the underlying permutation, capacity, output length, padding, and domain separation. A sponge design is not automatically secure simply because it uses a large internal state.

Practical note: SHA3-256 and SHA-256 are secure general-purpose hash choices, but ordinary unkeyed hashes are not substitutes for message authentication. Use a suitable MAC construction (such as HMAC or KMAC) when authenticity is required, and use password-specific hashing such as Argon2id to store passwords.

8. Check your understanding

1. Why is the internal state divided into rate and capacity?

The rate portion is used for message injection and output extraction. The capacity portion is not directly exposed and supports the security margin; together they make up the full state width.

2. In SHA3-256, what are r, c, and b?

r = 1088 bits, c = 512 bits, and b = 1600 bits.

3. What happens during absorbing?

Each padded r-bit message block is XORed into the rate portion, and the full-state Keccak-f[1600] permutation is applied.

4. What happens during squeezing?

Output bits are read from the rate part of the state. For longer output, the full-state permutation is applied again to generate another output segment.

5. What are the five Keccak round operations?

Theta, rho, pi, chi, and iota, applied in that order in each of 24 rounds.

6. Why are Keccak-256 and SHA3-256 hashes different?

They use different suffix and domain-separation padding conventions despite sharing the Keccak permutation and the same rate/capacity parameters.

7. Why does SHA3-256 need only one squeeze segment?

Its 256-bit digest is shorter than its 1088-bit rate; the needed bits are available immediately after the absorbing phase.

9. Key formulas

State width: b = r + c

Absorb: Sᵢ₊₁ = f(Sᵢ ⊕ (Pᵢ ∥ 0ᶜ))

Squeeze: Z = first ℓ bits of rate(S) ∥ rate(f(S)) ∥ …

SHA3-256: (b, r, c, output) = (1600, 1088, 512, 256)
