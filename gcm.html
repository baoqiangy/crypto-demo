Authenticated Encryption

GCM (Galois/Counter Mode)

AES-GCM: confidentiality, integrity, and authentication in one construction

1. What is GCM?

Galois/Counter Mode (GCM) is an authenticated-encryption-with-associated-data (AEAD) mode of operation for block ciphers, most commonly AES. It combines Counter (CTR) mode for encryption with GHASH, a polynomial-based authentication function over the finite field GF(2128).

For an input plaintext P, associated data A, secret key K, and a unique initialization vector (IV, often called a nonce), GCM outputs ciphertext C and an authentication tag T. Associated data is authenticated but not encrypted.

GCM provides: confidentiality of plaintext, integrity of the ciphertext and associated data, and authentication by a party holding the shared secret key. It does not provide digital signatures or automatic replay prevention.

2. Architecture: CTR encryption + GHASH authentication

Two parallel functions: CTR turns plaintext into ciphertext, while GHASH processes the authenticated inputs. The tag then combines the GHASH result with a secret AES-derived block.

3. Mathematical steps (AES-GCM)

Step 1: Generate the hash subkey

H = EK(0128)

Here EK means AES encryption under key K, and 0128 is a 128-bit zero block. The resulting H is a hash subkey used by GHASH, not the AES key itself.

Step 2: Build the initial counter block

For the recommended 96-bit IV, append 31 zero bits followed by a one bit:

J0 = IV ∥ 031 ∥ 1

For other IV lengths, the standard derives J0 using GHASH. The first plaintext block uses inc32(J0), not J0, as its counter block.

Step 3: Encrypt plaintext with counter mode

Ci = Pi ⊕ EK(inc32i(J0)),   i = 1, 2, …

The counter increment operates on the rightmost 32 bits. For the final partial block, only the required keystream bytes are used. Because blocks can be processed independently, GCM is well suited to parallelized encryption.

Step 4: Authenticate AAD and ciphertext

GHASH processes the concatenation of AAD (padded to 128-bit blocks), ciphertext (likewise padded), and one final 128-bit length block containing the bit lengths of AAD and ciphertext:

S = GHASHH(A ∥ pad(A) ∥ C ∥ pad(C) ∥ [len(A)]64 ∥ [len(C)]64)

GHASH operates over GF(2128). Multiplication and addition occur in this binary finite field; field addition corresponds to XOR.

Step 5: Generate the authentication tag

T = MSBt(EK(J0) ⊕ S)

The authentication tag is usually 128 bits (16 bytes); some protocols permit shorter tags, subject to stricter security limits. The tag is transmitted along with the ciphertext and nonce.

4. Conceptual worked example

Suppose a sender wishes to encrypt a short message and authenticate an unencrypted application header:

Secret AES key:     shared key K (128, 192, or 256 bits)
Nonce (96 bits):    00112233445566778899aabb
AAD:                type=payment;version=1
Plaintext:          Transfer $500
  1. Compute H = AES_K(0^128) and J0 = nonce || 00000001.
  2. Encrypt the plaintext with AES counter blocks beginning at inc32(J0), producing ciphertext C.
  3. Run GHASH over the AAD, ciphertext, and their encoded lengths to produce S.
  4. Compute the tag T = AES_K(J0) XOR S (using a 128-bit tag).
  5. Send nonce || ciphertext || tag plus the AAD, which need not be encrypted.

This example specifies the processing flow rather than invented ciphertext or tag values: those depend on the actual AES key. The Python example below generates real values.

5. Receiver verification and decryption

The receiver takes the shared key, IV, ciphertext, AAD and tag. It recomputes the expected authentication tag and checks it securely. Unauthenticated plaintext must not be released to the application. If the tag is invalid, decryption fails and the message is rejected.

What is AAD? Associated Authenticated Data might be a packet header, sequence number, message type, or protocol version. It is visible but cryptographically bound to the ciphertext. Altering AAD will cause verification to fail.

6. Python example: AES-GCM

Requires the cryptography package (pip install cryptography). The high-level AESGCM API performs encryption, tag generation, and verification.

from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

key = AESGCM.generate_key(bit_length=256)
aesgcm = AESGCM(key)

nonce = os.urandom(12)  # 96-bit unique nonce for this key
plaintext = b"Transfer $500"
aad = b"type=payment;version=1"

# encrypt() returns ciphertext followed by a 16-byte tag.
encrypted = aesgcm.encrypt(nonce, plaintext, aad)
ciphertext, tag = encrypted[:-16], encrypted[-16:]
print("Nonce:", nonce.hex())
print("Ciphertext:", ciphertext.hex())
print("Tag:", tag.hex())

# Receiver: verify tag and decrypt; raises InvalidTag on failure.
recovered = aesgcm.decrypt(nonce, ciphertext + tag, aad)
print("Recovered:", recovered.decode())

To demonstrate integrity protection, change one ciphertext byte, one AAD byte, or one tag byte, then attempt decryption. The library rejects the message.

7. Critical security considerations

Never reuse a nonce with the same AES-GCM key. Nonce reuse can expose relationships between plaintexts and can severely undermine authentication, potentially enabling forgeries. A nonce need not be secret, but uniqueness for a given key is essential.
  • Use a 96-bit nonce when possible; construct it using a reliably unique method. Random 96-bit nonces can be appropriate under bounded usage, but birthday-collision risk must be managed.
  • Keep keys secret and rotate them before protocol-specific data/nonce limits are reached.
  • Use full-length 128-bit tags unless a specification explicitly justifies a shorter tag.
  • Verify before use: reject malformed ciphertext and invalid tags without exposing the decrypted content.
  • Replay protection is separate: a valid message can be replayed. Use authenticated sequence numbers, nonces plus receiver-side tracking, or protocol replay windows.
  • Use vetted cryptographic libraries. Do not manually implement GHASH or nonce management for production systems.

8. GCM compared with CCM

FeatureGCMCCM
EncryptionCounter mode (CTR)Counter mode (CTR)
AuthenticationGHASH over GF(2128)CBC-MAC
Associated dataSupportedSupported
Parallel processingHighly parallelizableAuthentication chaining is sequential
Typical nonce96 bits recommended7–13 bytes for AES-CCM
Tag choicesTypically 128 bitsCommonly 32–128 bits in specified increments

Both are AEAD constructions. The best choice depends on the protocol, interoperability, implementation constraints, and nonce-management model.
