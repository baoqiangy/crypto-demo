Why Secure Signatures Must Bind Messages to Properly Checked Encodings

An explanation using textbook RSA, existential forgery, strict encoding verification, and RSA-PSS.

“A secure signature scheme must bind the message to a properly checked encoding.”

This means a digital signature must be cryptographically tied not only to the message being signed, but also to an unambiguous, correctly structured representation of that message. The verifier must check that structure carefully before accepting the signature.

This is particularly important for RSA digital signatures, because RSA's mathematical operation alone does not guarantee signature security.

1. Why is message encoding necessary?

Consider textbook RSA signatures. Let:

  • n = pq: RSA modulus
  • e: public exponent
  • d: private exponent
  • m: message represented as an integer

The signer computes:

s = md mod n

The verifier checks:

se mod n =? m

This looks reasonable, but it is insecure.

Example: Existential forgery against textbook RSA

An attacker who knows only the public key (n, e) can:

  1. Choose an arbitrary integer s.
  2. Compute m = se mod n.
  3. Announce (m, s) as a valid message-signature pair.

Verification succeeds automatically because:

se mod n = m

The attacker never needed the private key.

The problem: Textbook RSA accepts any mathematical value in the appropriate range as a valid message representative. It doesn't distinguish a properly formatted message from an arbitrary integer.

2. What does “bind the message to an encoding” mean?

Instead of signing the raw integer m, a secure scheme first transforms the message M into an encoded representation:

EM = Encode(M)

For RSA, the signature operation then applies the RSA private exponent to a representative derived from that encoding:

s = OS2IP(EM)d mod n

Here, OS2IP converts the encoded byte string into an integer. The encoding should incorporate a cryptographic hash of the message and any other values or structure required by the signature scheme.

Binding means that the encoding has a strong cryptographic relationship with the exact message being verified.

For example, when the encoding includes:

H(M) = SHA256(M)

Changing even one bit of M will, with overwhelming probability, produce a different hash and therefore a different expected encoding. This prevents an attacker from taking a valid signature on one message and using it to authenticate a different message.

3. Why must the encoding be properly checked?

Even if a signature scheme uses hashing and padding, verification can still be vulnerable if the verifier accepts malformed encodings.

Consider a simplified encoded message:

+----------+------------+------------------+-----------+
| Header   | Padding    | SHA-256(M)       | Trailer   |
+----------+------------+------------------+-----------+

A secure verifier must ensure that the entire encoding is valid, not merely that the expected message hash appears somewhere in the recovered data.

For example, suppose a verifier:

  1. Computes v = se mod n.
  2. Converts v into a byte string.
  3. Searches the byte string for SHA256(M).
  4. Accepts if the hash is found, ignoring other malformed bytes.

This is dangerous. An attacker might construct a signature whose RSA verification output contains the expected hash but does not satisfy the signature scheme's required encoding. The verifier could then accept a signature that the legitimate signing algorithm would never have produced.

This is the principle behind certain RSA signature forgery attacks involving lax PKCS#1 v1.5 verification, especially implementations using the small public exponent e = 3.

4. How RSA-PSS addresses this problem

RSA-PSS (Probabilistic Signature Scheme) is a modern RSA signature scheme standardized in RFC 8017.

Instead of directly signing the message hash, PSS constructs an encoded message using:

  • A cryptographic hash of the message
  • A random salt
  • A mask generation function, typically MGF1
  • Precisely specified encoding fields and bit constraints

Conceptually:

M → Hash + Salt + PSS Encoding → EM
s = EMd mod n

During verification:

EM′ = se mod n

The verifier then checks the PSS encoding, including the trailer, masked fields, salt-related hash computation, and relevant bit constraints. The signature is accepted only when all required checks succeed.

An arbitrary value produced by exponentiation is therefore overwhelmingly unlikely to be accepted as a valid encoding for the supplied message.

Notation note: These formulas suppress the standard byte-string/integer conversions for readability.

5. Important distinction: Hashing alone is not enough

A common misunderstanding is:

“If we hash the message before signing it, RSA signatures become secure.”

That is not generally true. Simply computing

s = H(M)d mod n

is not the same as using a standardized, provably secure RSA signature scheme.

A cryptographic hash is important, but secure signature construction also depends on the encoding, domain separation where appropriate, verification rules, and underlying security assumptions.

In particular, RSA-PSS has well-studied security properties under appropriate assumptions, while ad hoc hash-and-sign constructions should not be presumed secure.

6. Final interpretation

“Bind the message” means the verified signature must authenticate the exact message, rather than merely satisfy an RSA mathematical equation or match some unrelated data.

“Properly checked encoding” means the verifier must enforce every structural and cryptographic requirement defined by the signature scheme, rejecting malformed or incomplete encodings.

In mathematical terms, a secure verifier should implement:

Verify(pk, M, s) = { 1 if all signature and encoding checks pass; 0 otherwise }
Key takeaway: RSA exponentiation proves only a mathematical relationship. A secure signature scheme must additionally establish that the relationship authenticates the intended message through a correctly constructed and rigorously verified encoding.

That is why cryptographic applications should use standardized schemes such as RSA-PSS, rather than textbook RSA or custom padding and verification rules.
