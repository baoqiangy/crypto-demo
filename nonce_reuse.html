Nonce Reuse in Cryptography

Why reusing a nonce can compromise encrypted messages and authentication

1. What is a nonce?

A nonce (number used once) is a value supplied to a cryptographic operation that must satisfy a protocol-specific freshness or uniqueness requirement. In AES-CTR, AES-GCM, and AES-CCM, a critical rule is that the same nonce must not be reused with the same encryption key.

A nonce is generally not secret. Its job is to make different invocations operate differently, even if the same key is reused. In some protocols it is randomly generated; in others it is a counter. Random generation alone does not guarantee uniqueness.

Key distinction: A key must remain secret. A nonce generally may be public, but its required uniqueness must be enforced.

2. How nonce reuse breaks CTR-mode confidentiality

Counter (CTR) mode encrypts plaintext by XORing it with a keystream generated from the key and nonce/counter inputs.

C = P ⊕ S   where   S = CTR-Keystream(K, nonce)

If two messages are encrypted under the same key and nonce, CTR mode generates the same keystream positions for both messages:

C₁ = P₁ ⊕ S   and   C₂ = P₂ ⊕ S
C₁ ⊕ C₂ = P₁ ⊕ P₂

The keystream cancels out. The attacker learns the XOR of the two plaintexts. If one plaintext is known or can be guessed, the corresponding bytes of the other plaintext can be recovered.

Nonce reuse causes a repeated keystream in CTR mode. This is often called a “two-time pad” failure.

Small byte-level example

Suppose two one-byte plaintexts are encrypted using the same one-byte keystream value:

P₁ = 0x41   ('A')       P₂ = 0x42   ('B')
S  = 0x5A               S  = 0x5A    (reused)
C₁ = 0x41 ⊕ 0x5A = 0x1B
C₂ = 0x42 ⊕ 0x5A = 0x18

C₁ ⊕ C₂ = 0x1B ⊕ 0x18 = 0x03
P₁ ⊕ P₂ = 0x41 ⊕ 0x42 = 0x03

If P₁ is known:
P₂ = C₁ ⊕ C₂ ⊕ P₁ = 0x42  ('B')

This example uses toy values only to illustrate the XOR relationship; real AES-CTR keystream blocks are 128 bits.

3. Why nonce reuse is especially dangerous in AES-GCM

AES-GCM combines CTR-mode encryption with GHASH-based authentication. Reusing a nonce under the same AES key can damage both confidentiality and integrity:

  • Confidentiality failure: The CTR keystream repeats, revealing the XOR of the plaintexts at matching positions.
  • Authentication failure: Reusing the nonce also exposes algebraic relationships between GHASH authentication tags. Under suitable conditions, an attacker can recover information about the authentication subkey and create valid forgeries.
Critical: AES-GCM nonce reuse is not merely a reduction in security strength. A single repeated nonce can have serious consequences. Do not rely on a longer authentication tag to fix nonce reuse.

In standard 96-bit-nonce AES-GCM, the starting counter block J₀ is determined from the nonce, so repeating the nonce repeats the encryption counter sequence.

4. What about AES-CCM?

AES-CCM combines CTR encryption with CBC-MAC authentication. The nonce is incorporated into both the counter construction and authenticated formatting. Repeating the same nonce with the same key repeats the CTR keystream, compromising confidentiality. CCM also requires nonce uniqueness for its security guarantees; implementations must not assume its MAC makes reuse harmless.

5. Common causes of accidental nonce reuse

  • Counter reset: A device reboots and restarts its nonce counter at zero with the old key.
  • Cloned state: Two devices share a key and both start from the same nonce.
  • Random collision: Independently sampled nonces eventually collide (birthday effect).
  • Software bugs: A nonce is cached, hard-coded, reused after retries, or derived from a repeated timestamp.
  • Distributed senders: Multiple servers encrypt under the same key without coordinating nonce allocation.

Birthday-collision approximation

For independently and uniformly random n-bit nonces, after q encryptions, the approximate probability of at least one collision (when it is small) is:

Pr[collision] ≈ q(q − 1) / 2n+1

For a 96-bit random nonce and one million encryptions with a single key, this approximation is about 6.3 × 10−18. This is small, but the probability increases as the number of invocations grows. Protocol and implementation limits still apply.

6. Preventing nonce reuse

  1. Use a secure, established AEAD library. Avoid implementing GCM or CCM yourself.
  2. Guarantee uniqueness per key. Use a reliably managed counter or a protocol-approved nonce construction. If random nonces are used, observe strict per-key message limits.
  3. Protect state across restarts. A monotonic counter must not roll back after a crash, restore, or device clone.
  4. Partition nonce space across senders. Give senders disjoint nonce prefixes or separate keys.
  5. Rotate keys before limits are reached. Account for nonce space, number of encryptions, message lengths, and applicable protocol specifications.
  6. Use a misuse-resistant AEAD if nonce duplication is a realistic concern. AES-GCM-SIV can mitigate accidental reuse, but it does not make unlimited reuse acceptable.
Rule to remember: The nonce does not need to be secret, but the same (key, nonce) pair must not be repeated in AES-GCM, AES-CCM, or AES-CTR.

7. Python example with AES-GCM

The following example demonstrates safely using a fresh random 96-bit nonce for each encryption using the cryptography library.

import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)
aesgcm = AESGCM(key)

plaintext = b"Transfer $500"
aad = b"transaction-v1"  # authenticated, not encrypted

# Generate a new nonce for each encryption with this key.
nonce = os.urandom(12)  # 96 bits
ciphertext_and_tag = aesgcm.encrypt(nonce, plaintext, aad)

# Receiver needs the nonce, ciphertext/tag, shared key, and AAD.
recovered = aesgcm.decrypt(nonce, ciphertext_and_tag, aad)
assert recovered == plaintext

# Never use this same key + nonce pair for another encryption.

Note: Random 96-bit nonces are a common approach for applications with appropriate usage bounds, but the code itself does not keep a persistent record of previously generated nonces. Systems requiring hard uniqueness should manage nonce allocation explicitly.

8. Nonce reuse versus replay attacks

Nonce reuseReplay attack
Two or more encryption operations use the same nonce and key.An attacker retransmits an earlier valid message.
Can reveal plaintext and break cryptographic authentication.Can trick a receiver into processing an old valid request again.
Prevented by correct nonce allocation and key management.Prevented by freshness checks, sequence numbers, and replay detection.

Important: A unique encryption nonce does not automatically provide replay protection. A receiver must still reject previously accepted messages where the application requires it.
