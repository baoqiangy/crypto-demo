Authenticated Key Agreement Workflow

Identity authentication, shared-secret establishment, key derivation, and key confirmation

Authenticated key agreement (AKA) is a protocol in which two parties establish a fresh shared cryptographic secret while obtaining assurance about the identity of the peer associated with that secret. It addresses the main weakness of unauthenticated Diffie–Hellman: an active attacker can replace public key shares and establish separate secrets with each party.

Core idea: A shared secret alone does not identify your peer. A secure protocol binds the identities, exchanged key shares, negotiated parameters, and protocol transcript to cryptographic authentication and key derivation.

1. Goals and terminology

Security goals

  • Peer authentication: Know which peer the resulting key is associated with.
  • Key secrecy: Outsiders cannot derive the session key.
  • Key freshness: New session inputs produce fresh keys.
  • Transcript binding: Prevent substitution of identities, shares, or algorithms.
  • Forward secrecy: Past session keys remain protected if long-term authentication keys are compromised later (with ephemeral DH and suitable assumptions).

2. End-to-end workflow

Conceptual mutually authenticated signed ephemeral-DH workflow; actual standardized protocols may use a different message order and authentication format.

  1. Establish trusted identity information. Each side knows an authentic way to validate the other, such as a trusted certificate chain, pinned public key, or provisioned pre-shared key. Checking a certificate also requires validating its subject, intended usage, validity, and trust policy.
  2. Generate fresh ephemeral DH key shares. Alice chooses a and sends X = g^a; Bob chooses b and sends Y = g^b. In practice use validated groups or modern curves such as X25519 and reject invalid inputs as specified by the protocol.
  3. Authenticate the exchange. Bob signs or otherwise authenticates the transcript including identities, roles, key shares, nonces, and negotiated algorithms. Alice verifies with Bob's trusted authentication key. For mutual authentication, Alice authenticates her corresponding transcript as well.
  4. Calculate a common DH secret. Alice computes Z = Y^a mod p; Bob computes Z = X^b mod p. With an untampered exchange both equal g^(ab) mod p.
  5. Derive purpose-specific keys. Apply a suitable KDF such as HKDF with the negotiated context and transcript. Derive separate client-to-server and server-to-client encryption keys, IV material, and confirmation keys as needed. Do not use the raw DH secret directly as an AES key.
  6. Confirm and use keys. An authenticated Finished message or key-confirmation MAC proves possession of derived keying material and binds the session transcript. Abort on any failed authentication, invalid share, or confirmation mismatch.

3. Core equations

Alice: X = ga mod p
Bob: Y = gb mod p
Alice: ZA = Ya mod p
Bob: ZB = Xb mod p
ZA = ZB = gab mod p

In an illustrative signed-DH design, the peers authenticate the transcript and derive keys:

TH = Hash(protocol_id || identities || roles || algorithms || nonces || X || Y)
sigB = Sign(skB, context_B || TH)
PRK = HKDF-Extract(salt, Encode(Z))
KA→B = HKDF-Expand(PRK, "A-to-B" || TH, keyLen)
KB→A = HKDF-Expand(PRK, "B-to-A" || TH, keyLen)

These equations illustrate design concepts; they are not a complete new protocol specification. Real protocol security depends on exact encoding, domain separation, algorithm negotiation, identity validation, and message sequencing.

5. Why authentication defeats the basic MITM attack

In unauthenticated DH, Eve may intercept Alice's share X and Bob's share Y, substitute her own shares, and create separate session secrets with each side. Alice and Bob cannot detect the substitution from DH arithmetic alone.

In authenticated key agreement, Eve cannot successfully replace a DH share without also producing a valid authentication value for the resulting transcript under the trusted peer's secret authentication key. Assuming sound cryptography, correct credential validation, and secure key handling, that substitution is detected.

6. Important design pitfalls

  • Trusting an unverified certificate: A signature is useful only if its verification key genuinely belongs to the intended peer.
  • Signing just one public share: Failure to bind both peer identities, roles, and session context can enable identity-misbinding or unknown-key-share problems.
  • Ignoring negotiated algorithm choices: An attacker may attempt downgrade or cross-protocol confusion if relevant parameters are not protected.
  • Using static DH without considering forward secrecy: Long-term key compromise can expose recorded past sessions, depending on protocol design.
  • Reusing secrets or exposing traffic early: Do not release sensitive application data before the required authentication checks; protocols that support early data require additional replay defenses.
  • Confusing key agreement with key confirmation: Both parties calculating the same secret does not necessarily prove to either party that the other has derived or accepted the session key.

7. Real-world example: TLS 1.3

TLS 1.3 commonly uses ephemeral (EC)DHE to agree on a shared secret and HKDF to derive traffic keys. In certificate-based server authentication, the server's CertificateVerify message authenticates the handshake transcript, and Finished verifies its integrity and possession of handshake keying material. The server is authenticated; client authentication is optional and can be certificate-based. TLS 1.3 has additional details, including transcript hashes, traffic-secret stages, and optional PSK modes.

Keep the concepts separate: DH supplies a common secret; certificates/signatures or PSKs establish who is involved; HKDF derives keys; and Finished/key confirmation binds the handshake and checks possession of derived material.
