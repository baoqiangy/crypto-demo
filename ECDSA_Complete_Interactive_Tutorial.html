Elliptic Curve Digital Signature Algorithm (ECDSA)

The Elliptic Curve Digital Signature Algorithm (ECDSA) is a public-key cryptographic algorithm used to generate and verify digital signatures.

ECDSA is closely related to the Digital Signature Algorithm (DSA), but instead of using modular exponentiation, it uses elliptic curve point multiplication. A 256-bit elliptic curve key provides roughly 128-bit classical security, comparable to RSA with a 3072-bit modulus.

1. How ECDSA works

ECDSA uses a private key d, a secret integer for signing, and a public key Q, a point on an elliptic curve for verification. The signature is a pair of integers:

(r, s)
ECDSA signing and verification process

Conceptual flow: the receiver uses the received message and signature, not the sender's private key.

The three main phases are key generation, signature generation, and signature verification.

2. Elliptic curve mathematics

ECDSA commonly uses an elliptic curve over a finite prime field:

y2 ≡ x3 + ax + b (mod p)

Here p is a prime, a and b are curve coefficients, and (x,y) is a point on the curve. A nonsingular curve satisfies:

4a3 + 27b2 ≢ 0 (mod p)
Example elliptic curve over the real numbers

Illustration over the real numbers. Actual ECDSA works with discrete elliptic-curve points over a finite field.

Point addition

For distinct points P=(x1, y1) and Q=(x2, y2), with different x-coordinates, calculate:

λ = (y2 − y1)(x2 − x1)−1 mod p
x3 = (λ2 − x1 − x2) mod p
y3 = [λ(x1 − x3) − y1] mod p

For point doubling P+P, use the slope:

λ = (3x12 + a)(2y1)−1 mod p

Special cases use the point at infinity 𝒪, the additive identity.

Scalar multiplication

Q = dG

The operation dG means adding the base point G to itself d times. Finding d from G and Q=dG is the elliptic curve discrete logarithm problem (ECDLP), believed difficult for appropriate parameters.

4. ECDSA signature generation

  1. Hash message M and derive the integer hash representative z using the appropriate leftmost bits of H(M).
  2. Choose a secret nonce 1 ≤ k ≤ n−1, unique for this private key.
  3. Compute the point R = kG = (xR, yR).
  4. Compute r = xR mod n.
  5. Compute s = k−1(z + rd) mod n.
R = kG,   r = xR mod n
s = k−1(z + rd) mod n

If r=0 or s=0, retry with a different nonce. The final signature is (r,s). The equation for s closely resembles traditional DSA; ECDSA derives r from a point's x-coordinate.

5. ECDSA signature verification

  1. Check 1 ≤ r,s ≤ n−1.
  2. Recompute the same message hash representative z.
  3. Compute w = s−1 mod n.
  4. Compute u1 = zw mod n and u2 = rw mod n.
  5. Compute X = u1G + u2Q.
  6. If X=𝒪, reject. Otherwise let X=(xX, yX) and compute v = xX mod n.
  7. Accept if and only if v=r.
X = u1G + u2Q
Accept iff v = xX mod n = r

Real implementations must additionally use approved domain parameters and validate the public key.

7. Example 3: What if the message changes?

Suppose the attacker changes the message so its hash representative becomes z′=6 but keeps the original signature (10,6).

w=16,   u1 = 6×16 mod 19 = 1
u2 = 10×16 mod 19 = 8
X = G + 8Q = G + 56G = 57G = 𝒪

Since 57=3×19, X is the point at infinity and verification rejects.

✕ Signature rejected.

9. Why does ECDSA verification work?

Recall the signing equation:

s = k−1(z + rd) mod n

Multiply by k:

ks ≡ z + rd (mod n)

Since w=s−1 mod n:

k ≡ zw + rdw (mod n)

Using u1=zw mod n and u2=rw mod n:

k ≡ u1 + du2 (mod n)

During verification, the public key Q=dG gives:

X = u1G + u2Q
= (u1 + du2)G = kG = R

Because X and R are the same point, their x-coordinates match, so v=r.

10. Critical security issue: Reusing nonce k

Reusing the same secret nonce k with the same private key for two different messages can disclose the private key.

s1 = k−1(z1 + rd) mod n
s2 = k−1(z2 + rd) mod n

Subtract and solve for k:

k = (z1 − z2)(s1 − s2)−1 mod n

Then recover d:

d = (s1k − z1)r−1 mod n

Numerical example: Private-key recovery

Continue with n=19, d=7, k=3, and r=10.

Biased or partly leaked nonces also create serious risks. Deterministic nonce generation as specified in RFC 6979 reduces reliance on fresh randomness when properly implemented.

12. ECDSA versus EdDSA

EdDSA, including Ed25519, is another elliptic-curve-based signature family. ECDSA and EdDSA differ in their equations, curves, point encodings, and implementation requirements.

Ed25519 incorporates deterministic signing in its standard design and does not require generation of a fresh random ECDSA-style nonce for every signature. Both schemes can be secure with suitable parameters and correct implementations.
