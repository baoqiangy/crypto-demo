SYMMETRIC-KEY AUTHENTICATION

Needham–Schroeder Symmetric-Key Protocol

A classic five-message protocol for mutual authentication and establishing a shared session key through a trusted Key Distribution Center (KDC).

1. Purpose and participants

The Needham–Schroeder symmetric-key protocol (1978) lets Alice and Bob establish a temporary shared key without already sharing a direct long-term key with each other. They instead trust a central server, S, that knows a long-term secret key for each participant.

SymbolMeaning
A, B, SAlice, Bob, and the trusted authentication/key-distribution server
K_ALong-term symmetric key shared only by Alice and S
K_BLong-term symmetric key shared only by Bob and S
K_ABNew session key intended for Alice and Bob
N_A, N_BFresh, unpredictable nonces chosen by Alice and Bob
{X}_KMessage X encrypted with the symmetric key K
N_B − 1A prescribed transformation of Bob's nonce, showing it was decrypted
Trust assumption: Alice and Bob trust S to issue genuine session keys and keep their long-term keys secret. Secure authenticated encryption or appropriately authenticated encryption of protocol messages is needed in a modern design; the historical notation abstracts away these details.

2. The five protocol messages

1. A → S : A, B, N_A
2. S → A : { N_A, B, K_AB, { K_AB, A }_K_B }_K_A
3. A → B : { K_AB, A }_K_B
4. B → A : { N_B }_K_AB
5. A → B : { N_B − 1 }_K_AB

Message 2 includes a ticket for Bob, {K_AB, A}_K_B, protected by Bob's long-term key. Alice forwards it without being able to modify its encrypted contents.

Sequence diagram (not to scale). A → B traffic in steps 3–5 is protected with keys issued or referenced earlier.

Message 1 — Request a session keyA → S : A, B, N_AAlice identifies herself, names Bob as the intended peer, and includes a fresh nonce N_A to link the server's reply to this request.
Message 2 — Server issues a session key and ticketS → A : { N_A, B, K_AB, {K_AB, A}_K_B }_K_AS generates K_AB. Alice decrypts the outer message with K_A and checks N_A and Bob's identity. The nested ticket is intended for Bob.
Message 3 — Alice forwards Bob's ticketA → B : { K_AB, A }_K_BBob uses K_B to recover K_AB and the claimed identity of Alice. At this moment, Bob does not know whether the ticket is newly issued.
Message 4 — Bob challenges AliceB → A : { N_B }_K_ABBob sends a freshly chosen nonce encrypted using the session key. Someone without K_AB should not be able to answer correctly.
Message 5 — Alice answers the challengeA → B : { N_B − 1 }_K_ABAlice decrypts the challenge and returns the specified transformation. Bob verifies it, thereby confirming that the responder knows K_AB.

3. What the protocol achieves—and what it does not

PropertyExplanation
Key distributionS supplies a session key to Alice and Bob using their respective long-term keys.
Freshness for AliceN_A lets Alice tie S's encrypted response to her current request.
Proof of possession for BobMessages 4–5 show that the responder knows the ticket's session key.
Missing freshness guarantee for BobBob's ticket has no timestamp, lifetime, or Bob-generated freshness value; Bob cannot tell whether S issued it recently.

4. Denning–Sacco replay attack (compromised old session key)

The classic weakness arises if an attacker records an old ticket and later learns the corresponding old session key K_AB. The attacker can reuse the old ticket to impersonate Alice to Bob.

Key condition: Simply capturing a ticket is not enough to answer Bob's challenge. The attacker must also learn the old session key (for example, through a later compromise). The attack illustrates the risk of session-key compromise combined with ticket replay.
  1. In an earlier legitimate run, Eve records the encrypted ticket {K_AB, A}_K_B.
  2. Later, Eve obtains that session's old key K_AB.
  3. Eve replays the ticket to Bob, pretending to be Alice.
  4. Bob decrypts the ticket and sends a new nonce encrypted under the old session key.
  5. Because Eve knows that key, she decrypts the nonce and produces the correct response. Bob accepts her.

Why Bob's nonce is insufficient: The nonce proves possession of the key in the ticket, not that the key or ticket was recently created. A compromised old key can still answer a fresh challenge.

5. Defenses and protocol evolution

ApproachSecurity benefit / caveat
Ticket timestamps and expirationLimit ticket validity (an approach associated with Denning–Sacco and Kerberos). Require reasonable clock synchronization and replay controls within the validity window.
Bob-contributed freshnessBind an authenticated challenge or Bob's nonce into the server-issued key material/ticket, so replaying an older ticket does not satisfy a fresh request.
Short-lived session keysReduce exposure, but do not eliminate the problem if old tickets remain acceptable.
Replay cache and identifiersRemember and reject previously accepted authenticators or protocol instances.
Modern authenticated protocolsUse well-studied designs with explicit key confirmation, freshness, identity binding, and strong authenticated encryption.
Kerberos connection: Kerberos uses tickets and authenticators with timestamps and expiry, but is not simply the original five-message Needham–Schroeder protocol. Ticket lifetime, clock skew, replay-cache behavior, and key-management policies still matter.

7. Knowledge check

  1. Why does Alice include N_A in Message 1, and where is it checked?
  2. Why does S encrypt Bob's ticket using K_B rather than K_A?
  3. What does Bob learn from Messages 4–5? What does he not learn?
  4. What two pieces of information does Eve need for the Denning–Sacco replay attack?
  5. Would choosing a longer N_B solve the old-ticket replay problem? Explain.
  6. How could a timestamp and replay cache help, and what limitations do they have?

Key takeaway: A fresh challenge can prove possession of a session key without proving that the session key or ticket is fresh. Authentication protocols must bind identities, keys, and freshness together.
