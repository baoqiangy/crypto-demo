Understanding Replay Attacks

How captured, legitimate messages can be reused — and how secure protocols stop them.

A replay attack is an attack in which an adversary captures a legitimate message or authentication request and retransmits it later, hoping a receiver will treat the old message as a fresh, valid request. The attacker need not decrypt or modify the message.

1. How a replay attack works

  1. Alice sends a legitimate authentication or transaction request to Bob, the server.
  2. Eve intercepts or records the message.
  3. Eve retransmits the captured message.
  4. If Bob cannot distinguish old messages from new ones, he may accept the repeated request.

2. Example: Online banking

Suppose Alice sends an authenticated instruction to her bank:

From: Alice
To: Bank
Action: Transfer $500 to Account X
Authentication: Valid MAC

Eve captures and replays this request three more times. Without replay protection or transaction deduplication, the bank might execute additional transfers.

Why isn't a MAC enough? A valid message authentication code (MAC) protects authenticity and integrity, but by itself it does not prove that a request is fresh or has not been processed before.

3. Defenses against replay attacks

DefenseHow it helps
NonceA unique one-time value can identify reused requests when the receiver verifies it and rejects duplicates.
TimestampLimits a request's lifetime. Duplicate detection is still necessary during the allowed time window.
Sequence numberAllows the receiver to detect repeated or out-of-window messages.
Challenge-responseRequires the client to authenticate a newly issued challenge rather than reuse an old response.
Unique transaction IDSupports deduplication so repeated requests do not execute the same transaction twice.

4. Example: A nonce with an HMAC

Message: Transfer $500
Nonce: 847291
MAC: HMAC(secret_key, Message || Nonce)

Bob validates the HMAC and checks whether nonce 847291 has already been accepted:

  • First request: Accepted; nonce is recorded.
  • Second request with the same nonce: Rejected.
  • Third request with the same nonce: Rejected.

The receiver must keep appropriate state and handle concurrent requests atomically. A nonce without receiver-side freshness validation is not sufficient.

5. Replay attack vs. man-in-the-middle attack

Replay attackMan-in-the-middle (MITM) attack
Records and reuses previously valid messages.Intercepts or positions itself between communicating parties.
Does not require altering the message.May relay, observe, or modify communications, depending on the protection in place.
Exploits missing message-freshness or duplicate checks.Exploits weaknesses in channel authentication or communication security.

A replay attack may be performed as part of a MITM attack, but the two concepts are not identical.

Key takeaway: Encryption protects confidentiality; a MAC protects integrity and message authenticity. Neither automatically establishes freshness. Anti-replay protections require explicit protocol mechanisms such as nonces, sequence numbers, challenge-response, or replay detection.
