Man-in-the-Middle Attack Against Unauthenticated Diffie–Hellman

Diffie–Hellman (DH) allows two parties to establish a shared secret over an insecure channel. Unauthenticated DH does not prove who sent the public values, so an active attacker can replace them and establish a different secret with each party.

1. Normal Diffie–Hellman Exchange

Alice and Bob publicly agree on a prime p and generator g. Alice chooses a private exponent a, and Bob chooses b.

Alice sends A = ga mod p
Bob sends B = gb mod p
Both compute K = gab mod p

A passive eavesdropper sees p, g, A, B, but for well-chosen cryptographic groups cannot feasibly recover the shared secret merely from these values.

2. Active Man-in-the-Middle Attack

Eve intercepts the public DH values before delivery. Instead of forwarding Alice’s value A to Bob, Eve sends her own Y. Instead of forwarding Bob’s value B to Alice, Eve sends her own X.

Alice ↔ Eve

Alice receives X = gˣ mod p, believing it came from Bob.

KAE = Xa = Ax mod p

Eve ↔ Bob

Bob receives Y = gʸ mod p, believing it came from Alice.

KBE = Yb = By mod p

When Alice sends encrypted traffic, Eve decrypts it with KAE, optionally changes it, then re-encrypts it with KBE for Bob. The reverse direction works similarly.

3. Worked Numerical Example

Important: These tiny numbers demonstrate the arithmetic only. They are completely insecure for real cryptography.

Choose p = 23, g = 5. Alice chooses a = 6; Bob chooses b = 15. Eve chooses x = 7 for Alice’s side and y = 11 for Bob’s side.

Key on Bob’s side

Bob: KBE = 2215 mod 23 = 22
Eve: KBE = 1911 mod 23 = 22
Result: Alice shares key 12 with Eve, while Bob shares key 22 with Eve. Neither realizes that Eve replaced the public DH values. Without interference, Alice and Bob would instead obtain 196 mod 23 = 2.

4. Why Can This Happen?

The mathematical DH exchange establishes a secret with the holder of the corresponding private exponent, but does not establish that this holder is the intended peer. A secure encryption algorithm does not fix an unauthenticated key exchange: it may simply protect each of the two attacker-controlled connections.

5. How to Prevent the Attack

  1. Authenticate DH public values: Use digital signatures and verified certificates, or another reliable authenticated identity mechanism.
  2. Bind identities and the handshake transcript: Authentication must cover the actual exchanged key shares and relevant protocol context, preventing value substitution and unknown-key-share confusion.
  3. Use authenticated pre-shared-key protocols: Properly designed PSK-authenticated handshakes can provide peer authentication without certificates.
  4. Verify key confirmation: An authenticated confirmation tied to the negotiated key and transcript helps detect inconsistencies. Bare, unauthenticated key confirmation alone is not a substitute for peer authentication.
  5. Use a vetted protocol: TLS 1.3 authenticates the handshake when certificate/identity validation is correctly performed; avoid inventing a custom DH protocol.
Core principle: A shared secret is not proof of peer identity. Secure key agreement requires authenticated key exchange.
