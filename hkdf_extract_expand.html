HKDF: Extract and Expand

HMAC-based Key Derivation Function · RFC 5869 · Cryptography

HKDF converts input keying material (IKM) into one or more cryptographically strong, purpose-specific keys. Its two stages have distinct roles: Extract produces a pseudorandom key (PRK), and Expand produces output keying material (OKM) of the requested length.

1. Why do we need HKDF?

A key exchange, such as Diffie–Hellman, produces shared secret material, but applications often need several separate keys: an encryption key, a MAC key, or keys for opposite communication directions. Directly reusing the same raw secret for every purpose is poor key-management practice.

HKDF makes it possible to derive distinct keys from one secret using HMAC and optional context information (info). It does not add entropy to a weak secret or turn a low-entropy password into a secure key on its own.

2. The two-stage architecture

3. HKDF-Extract

PRK = HMAC-Hash(salt, IKM)
ParameterMeaning
IKMInput keying material, such as a Diffie–Hellman shared secret
saltOptional nonsecret salt; if omitted, RFC 5869 uses HashLen zero bytes
PRKPseudorandom key; its length equals the hash output length
HashLenHash output size in bytes: 32 for SHA-256

For HKDF-SHA256, the Extract operation always produces a 32-byte PRK, regardless of the desired final key length. In this HMAC call, the salt is the HMAC key and IKM is the HMAC message.

Salt is not a nonce. The salt need not be secret. A suitable independent salt strengthens extraction and separates uses. HKDF can work with an omitted salt, but the RFC recommends using a salt where practical.

4. HKDF-Expand

Expand uses the PRK as the HMAC key and generates enough blocks to fill the requested output length L.

T(0) = empty string
T(i) = HMAC-Hash(PRK, T(i−1) || info || byte(i))
OKM = first L bytes of T(1) || T(2) || ... || T(N)
N = ceil(L / HashLen)

The byte(i) counter is exactly one byte: 0x01, 0x02, etc. The first block has no previous-block bytes because T(0) is empty.

For SHA-256, HashLen = 32 bytes. If L = 42 bytes, then N = ceil(42/32) = 2: produce 64 bytes from T(1) || T(2) and retain the first 42 bytes.

Output limit: RFC 5869 permits L ≤ 255 × HashLen. For HKDF-SHA256, the maximum output is 8160 bytes. Output length is measured in bytes, not bits.

6. Python: implement Extract and Expand

import hashlib
import hmac

def hkdf_extract(salt: bytes | None, ikm: bytes) -> bytes:
    hash_len = hashlib.sha256().digest_size
    if salt is None:
        salt = bytes(hash_len)
    return hmac.new(salt, ikm, hashlib.sha256).digest()

def hkdf_expand(prk: bytes, info: bytes, length: int) -> bytes:
    hash_len = hashlib.sha256().digest_size
    if len(prk) < hash_len:
        raise ValueError("PRK must be at least HashLen bytes")
    if not (0 <= length <= 255 * hash_len):
        raise ValueError("Invalid output length")
    output = b""
    previous = b""
    for counter in range(1, (length + hash_len - 1) // hash_len + 1):
        previous = hmac.new(
            prk, previous + info + bytes([counter]), hashlib.sha256
        ).digest()
        output += previous
    return output[:length]

# RFC 5869 Appendix A.1
ikm = bytes.fromhex("0b" * 22)
salt = bytes.fromhex("000102030405060708090a0b0c")
info = bytes.fromhex("f0f1f2f3f4f5f6f7f8f9")
prk = hkdf_extract(salt, ikm)
okm = hkdf_expand(prk, info, 42)

assert prk.hex() == (
    "077709362c2e32df0ddc3f0dc47bba63"
    "90b6c73bb50f9c3122ec844ad7c2b3e5"
)
assert okm.hex() == (
    "3cb25f25faacd57a90434f64d0362f2a"
    "2d2d0a90cf1a5a4c5db02d56ecc4c5bf"
    "34007208d5b887185865"
)
print("HKDF test vector passed")
Implementation note: This code is for understanding the algorithm. Production applications should generally use a maintained cryptographic library’s HKDF implementation rather than maintaining custom cryptographic code.

7. Deriving different keys with info

Keeping the same PRK but changing info derives different context-specific outputs:

encryption_key = hkdf_expand(prk, b"myapp/v1/encryption", 32)
authentication_key = hkdf_expand(prk, b"myapp/v1/authentication", 32)

The labels help enforce domain separation, so keys intended for different purposes are distinct. Use unambiguous encodings for protocol identifiers, algorithms, key directions, and contexts; the sender and receiver must agree exactly on the info value.

9. Security considerations and common mistakes

  • HKDF is not encryption: it derives keys; it does not encrypt or authenticate application messages.
  • IKM must have sufficient secrecy and entropy: HKDF cannot rescue a guessable password. For passwords, use a password-hardening KDF such as Argon2id or scrypt instead.
  • Protect the PRK and derived keys: they are cryptographic secrets. The salt and info need not be secret.
  • Do not confuse salt with info: salt affects Extract; info binds application context during Expand.
  • Use clear separation: different roles and traffic directions should have different info labels where the protocol requires distinct keys.
  • Be aware of protocol variants: systems such as TLS 1.3 use HKDF-based labeled derivations, not just plain HKDF with arbitrary strings.
