Tag Truncation in Cryptography

Message Authentication Codes · HMAC · CMAC · CCM · GCM

Tag truncation means shortening a message authentication code (MAC) or authentication tag by retaining a specified number of bits and discarding the rest. It reduces communication and storage overhead, but also lowers the resistance to forgery.

1. How tag truncation works

Suppose AES-GCM produces a 128-bit (16-byte) authentication tag. A protocol may transmit the leftmost 96 bits (12 bytes) instead.

Original authentication tag — 128 bits
8F2A91B7C3D4E506A1B2C3D4E5F60718
↓

Keep the leftmost 96 bits (24 hexadecimal digits)

8F2A91B7C3D4E506A1B2C3D4E5F60718

Green: 96 bits retained   ·   Red: 32 bits discarded

Tt = MSBt(T)

Here, T is the full authentication tag, t is the required tag length in bits, and MSBt means the leftmost t bits. The sender and receiver must agree on the truncation rule and tag length.

2. Why truncate authentication tags?

The principal advantage is efficiency. Shorter tags consume fewer bytes in a network packet, which can matter for low-bandwidth or resource-constrained devices.

For a 20-byte message, ignoring other protocol headers and overhead:

128 bits16 bytes36 bytes
96 bits12 bytes32 bytes
64 bits8 bytes28 bytes
32 bits4 bytes24 bytes

3. Security implications

For an ideal uniformly distributed t-bit authentication tag, a single independent random guess succeeds with approximate probability:

Pforge ≈ 1 / 2t
Tag lengthApproximate success probability per random guess
128 bits1 / 2128
96 bits1 / 296
64 bits1 / 264
32 bits1 / 232
Security caveat: These are simplified guessing probabilities, not complete security guarantees. Actual bounds also depend on the algorithm, number of verification attempts, message lengths, nonce management, key lifetime, and protocol constraints. In GCM, short tags require particularly strict limits.

4. How the receiver verifies a truncated tag

Suppose Alice and Bob share an HMAC key and agree to use the first 96 bits of HMAC-SHA256.

Message: Hello Bob
Tag:     First 96 bits of HMAC-SHA256(K, Message)
  1. Alice computes the full HMAC-SHA256 tag.
  2. Alice transmits the message and the first 96 bits of that tag.
  3. Bob computes the full HMAC-SHA256 tag using the received message and shared key.
  4. Bob extracts its first 96 bits and compares those bits with the received tag using a constant-time comparison.
  5. Bob accepts the message only if the tags match and all other protocol checks pass.

Changing the agreed tag length is not merely a display preference: it changes the security level of the protocol.

5. Tag truncation in common algorithms

AES-CCM128-bit internal CBC-MAC resultStandardized transmitted tag lengths: 32, 48, 64, 80, 96, 112, or 128 bits.
AES-GCM128 bitsNIST-specified lengths: 128, 120, 112, 104, 96, and restricted 64- or 32-bit cases. Short tags are not general-purpose defaults.

For general-purpose AES-GCM applications, a 128-bit tag is a sound default. Do not arbitrarily truncate a tag unless the specific protocol and implementation support that length and its security limits.

6. Does truncation change encryption?

No. In an authenticated-encryption mode such as AES-GCM, the encryption operation itself remains unchanged when only the authentication tag is shortened.

  • Confidentiality: AES Counter Mode protects plaintext from disclosure under the required security assumptions.
  • Integrity and authenticity: The authentication tag allows the receiver to detect forged or modified messages.
  • Truncation: Transmits fewer authentication bits, reducing forgery resistance.

Although encryption computations are unchanged, weakening authentication can undermine the security of the overall authenticated-encryption system.
