PKI Certificate Chain

A PKI certificate chain links a server's or user's public-key certificate to a trusted certificate authority (CA). Each link is checked so that a client can decide whether a public key belongs to the identity it intends to communicate with.

Core idea: A certificate is not trusted merely because it contains a digital signature. Trust depends on a valid chain of signatures ending at an accepted trust anchor, plus certificate-purpose, identity, validity, and other policy checks.

1. The three main certificate roles

The arrows indicate certificate issuance/signing; they do not mean the private keys are shared.

CertificatePurposeTypical location
Root CATop-level trust anchor, often signs intermediates rather than end-entity certificates.Preinstalled or explicitly trusted in a trust store.
Intermediate CADelegated authority that can sign leaf certificates and possibly other intermediates.Usually delivered by the server or obtained during path building.
Leaf (end-entity)Binds an identity (e.g., DNS name) to a public key, subject to certified usages.Presented by the TLS server.

2. What is inside an X.509 certificate?

An X.509 certificate contains signed to-be-signed certificate (TBSCertificate) data and a signature by its issuer. Relevant fields/extensions include:

Field or extensionWhat it tells the validator
Subject / Subject Alternative Name (SAN)Identities; TLS hostnames are matched against the DNS names in SAN.
IssuerIdentity of the CA purported to have issued the certificate.
Subject Public Key InfoThe public key and its algorithm.
Validity periodnotBefore and notAfter times.
Basic ConstraintsCA:TRUE for issuing CAs; CA:FALSE for ordinary leaf certificates. May limit subordinate CA depth.
Key Usage / Extended Key UsageAuthorized uses such as keyCertSign for CAs or serverAuth for TLS servers.
Authority/Subject Key IdentifiersHelp identify potential issuing certificates; do not replace signature checks.
Signature Algorithm / SignatureIssuer's cryptographic signature over the certificate contents.

3. How certificate-chain validation works

1

Build a candidate certification path. Starting from the leaf, locate its issuing intermediate(s) up to a configured trust anchor. A server often sends leaf and intermediates, but normally not the root.

2

Verify signatures. Check the leaf's signature using its issuer's public key, then the intermediate's signature using its issuer's public key, and so on. The trust anchor itself is accepted according to local trust configuration, not simply because it self-signed.

3

Enforce CA constraints. Issuing certificates must be authorized as CAs; validate basicConstraints, keyUsage, path-length constraints, name constraints, and relevant policies as applicable.

4

Check certificate dates and algorithms. Reject expired or not-yet-valid certificates, and reject disallowed cryptographic algorithms or insufficient key strengths according to policy.

5

Check the intended identity and purpose. For HTTPS, ensure the requested DNS hostname matches a SAN entry and the certificate is suitable for TLS server authentication.

6

Apply revocation and application policy. Evaluate CRLs, OCSP, stapled status, or browser-specific mechanisms when required by the client and environment. Revocation behavior varies across clients.

7

Authenticate the connection endpoint. During TLS, the server must demonstrate possession of the corresponding private key (for example, with TLS 1.3 CertificateVerify). A valid certificate by itself does not show that the peer owns the key.

Certificate verification ≠ data decryption: CA signatures authenticate the binding between identity and public key. TLS then uses an authenticated key exchange and symmetric traffic keys to protect application data.

4. Worked HTTPS example

A browser connects to https://www.example.com. Imagine the server presents:

Leaf:          DNS=www.example.com
  Issuer:      Example Issuing CA
  Signed by:   Example Issuing CA private key

Intermediate:  Example Issuing CA
  Issuer:      Example Root CA
  Signed by:   Example Root CA private key

Root anchor:   Example Root CA
  Trusted locally in browser/OS trust store

The client checks both issuer signatures, certificate constraints, validity dates, the DNS name www.example.com, suitable server authentication usage, and local trust/revocation policies. In TLS, the server additionally proves possession of its private key.

Verify(pkissuer, TBScertificate, signature) = true

This is a conceptual signature-verification expression. The exact inputs and verification rules depend on the X.509 signature algorithm.

5. Why use intermediate CAs?

  • Protect the root: A root private key can be kept offline while intermediate keys handle day-to-day issuance.
  • Delegate responsibility: Different intermediates can support different certificate types, customers, and policies.
  • Limit operational damage: A compromised intermediate can be revoked or replaced without necessarily replacing the root, though remediation can be complex.
  • Control path depth: Constraints can limit which certificates an intermediate may issue.

7. Chain building nuances

Cross-signing

The same CA public key can be certified by different issuers, creating alternative paths. Clients may build different valid chains depending on trust stores and path-building rules.

Trust stores are local policy

A private enterprise root may be accepted on managed devices yet rejected by public browsers. Being self-signed does not automatically make a root trustworthy.

Certificate Transparency (CT): Many browsers require publicly trusted TLS certificates to satisfy CT policies. CT provides public auditability of issuance, but it does not substitute for certificate-chain validation.

8. Practical inspection commands

On a machine with OpenSSL, inspect the certificates presented by a server:

openssl s_client -connect www.example.com:443 \
  -servername www.example.com -showcerts

Inspect a PEM certificate's subject, issuer, validity, SAN, and extensions:

openssl x509 -in server.pem -noout -text

These commands inspect certificate details; a successful manual inspection is not equivalent to a complete browser policy evaluation. Use certificates from an authorized test endpoint.

9. PKI certificate chain vs. digital signature vs. TLS

ConceptRole
Digital signatureCryptographically verifies signed data against a public key.
PKI certificate chainEstablishes a trust path for binding identity to public key, subject to validation rules.
TLS handshakeAuthenticates endpoint(s) and negotiates keys for secure communications.
Symmetric encryption / AEADProtects application data after key establishment.
